 # Module 4: Backend and Database Documentation

## Section 1 - Module Overview
The Backend and Database module serves as the central data persistence and business logic layer for the AI-Powered Smart PPE Inspection Station. Running on a Node.js 20 runtime with an Express.js 5 framework, it exposes a RESTful API to manage workers, roles, and safety compliance logs. It persists all operational data in a PostgreSQL relational database. The backend directly interacts with the IoT module, which pushes real-time inspection results, and the UI and UX module, which fetches configuration data and compliance statistics. By centralizing validation and storage, it acts as the authoritative source of truth in the system data flow.

## Section 2 - Background and Related Work
The team investigated multiple database paradigms, explicitly comparing NoSQL options with traditional relational databases like PostgreSQL. A relational database is selected because the problem domain requires strict relational integrity between registered workers, their assigned roles, and the specific personal protective equipment mandated for each role. PostgreSQL provides ACID compliance, which guarantees that entry transactions and their associated PPE detection details are saved atomically, preventing corrupt or partial compliance records.

The team also evaluated full-stack Node.js frameworks such as NestJS against minimalistic micro-frameworks like Express.js. Express.js is chosen because it carries a significantly lighter footprint and avoids the steep learning curve and boilerplate overhead of dependency injection containers. This allows the backend to remain tightly focused on serving the IoT module's REST API requests quickly without unnecessary software layers.

Additionally, raw SQL queries were compared against Object-Relational Mapping libraries. The Prisma ORM is adopted because it automatically generates type-safe database clients from a declarative schema model. This eliminates manual SQL syntax errors and seamlessly maps relational query results into nested JSON structures, reducing the controller logic required when communicating with the React-based UI and UX module.

## Section 3 - Methodology
The backend module is organized into a modular layered architecture consisting of routes, controllers, and Prisma data models. External HTTP requests are first filtered by Express middlewares that apply security headers via Helmet and enable Cross-Origin Resource Sharing. Valid requests are forwarded to endpoint-specific controller functions. The controllers extract payloads, apply business logic, and invoke the generated Prisma client to perform the necessary persistence actions. This structure is chosen because separating the HTTP routing from the business logic ensures that each component can be independently tested with mocked database inputs.

Data flows into the module exclusively via JSON payloads over HTTP REST. When a payload arrives at an endpoint, the controller validates the presence and type of required fields. The controller then translates the request into Prisma ORM commands, which convert the operation into parameterized raw SQL queries executed by the PostgreSQL engine. Once the database operation completes, the data flows back out to the client formatted as a structured JSON response containing the success status and the manipulated records.

A key design decision involves how inspection results are persisted. Instead of issuing independent database insert commands for a scan event and its individual equipment detections, the module wraps them in a single Prisma transaction. A transaction is used because physical hardware failures or network interruptions could occur precisely while a log is being recorded. If a failure happens, the transaction rolls back entirely, which guarantees that the database never contains floating detection records without a parent entry log.

The module operates globally and continuously behind the scenes to bridge the physical inspection station with human administrators. It remains persistently active, waiting for the active state machine of the IoT module to complete a cycle and transmit the outcome. Before it runs, states like worker roles exist in the database ready to be queried; after an API call completes, the system holds highly structured, persistently stored records of the gate's decision history.

## Section 4 - Inter-Module Communication
The backend communicates with the IoT module to enforce physical security and securely persist inspection outcomes. The IoT module depends on the backend to evaluate the scanned RFID card UID and return the worker's required PPE list. Without this communication, the IoT module would lack the specific rules needed to operate its inference engine correctly. This responsibility boundary exists because centralizing the business rules on the backend prevents the hardware station from needing frequent rule synchronization or local storage provisioning.

The backend also communicates with the UI and UX module to surface compliance insights to human administrators. The UI application depends on the backend to retrieve both granular tracking data and aggregated statistics, such as compliance rates and frequently missed equipment. This communication is strictly required so that safety administrators can actively configure the physical rules of the system from a remote PC interface, effectively decoupling the administrative control loop from the physical turnstile environment.

## Section 5 - Implementation
A non-obvious implementation challenge involves the graceful handling of unregistered personnel arriving at the inspection station. When the IoT module scans an unrecognized RFID card, it generates an entry log with an outcome of UNKNOWN_CARD. The backend implementation accommodates this by relaxing the worker relation constraint on the entry log table, allowing the worker ID to be completely null. This design satisfies the database foreign key requirements while ensuring that the station captures the exact time and camera snapshot URL of the illicit entry attempt for auditing purposes.

Another critical implementation detail is the dynamic calculation of missing personal protective equipment within the entry log controller. When an inspection is graded as a failure, the controller filters the saved detection details to identify items that were mandated by the worker's role but not detected by the AI vision models. It maps these missing items out dynamically and embeds them in the raw JSON response payload. This computationally trivial step prevents the calling client from needing to re-fetch the role requirements and perform a diff logic calculation on its side.

Finally, the backend implements database model mapping to synthesize strict database conventions with modern JavaScript paradigms. It utilizes the Prisma schema mapping directive to define tables and columns in standard snake case structure entirely within the PostgreSQL database representation. However, the generated Javascript code exposes these identical entities strictly using camel case identifiers. This implementation decision allows Node.js developers to maintain standard casing conventions in the application layer without compromising conventional database administrator naming schemes.

## Section 6 - Testing Strategy
The module is tested with Jest using two complementary layers: HTTP integration tests with Supertest for all exposed backend routes, and direct unit tests for shared middleware behaviors. Tests run during local development and before integration updates, with Prisma fully mocked so controller and middleware logic can be validated deterministically without provisioning a live PostgreSQL instance. The acceptance criteria require that each implemented route and middleware branch returns the expected status code or control-flow behavior, that validation failures produce the documented error structure, and that Prisma error paths are converted into stable server-error responses.

## Section 7 - Known Limitations and Open Issues
A known limitation of the backend implementation is the complete absence of authentication or authorization middleware on the exposed routes. The system fundamentally trusts all incoming requests, assuming they originate within a secure internal network environment. This limitation means an attacker with local network access could easily forge entry logs or tamper with the worker databases. Furthermore, the endpoints lack rate limiting, which exposes the Prisma application layer to potential stress if the hardware module malfunctions and rapidly spams API requests.

The foremost unresolved open issue revolves around the boundary mismatch between real-time data needs and the currently implemented architectural pattern. The API contract notes in project risk register entry R-08 that the display application requires real-time updates via WebSocket, yet the current implementation exclusively provisions standard HTTP REST endpoints. The technical dividing line over whether the backend will implement a native WebSocket server or if an intermediary streaming service will be established remains undecided. Similarly, project risk R-07 details concerns regarding the physical Wi-Fi reachability between the backend environment and the Raspberry Pi deployment location.
